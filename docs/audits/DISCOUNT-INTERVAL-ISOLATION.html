WAKA POS · Subscription billing audit

Monthly and Annual Discount Isolation

Every place the two billing intervals are currently joined together, why the join is structural rather than accidental, and the smallest change that separates them.

Date 12 Oct 2026 Scope Database, RPCs, admin UI, checkout, tests Status Implemented locally — not applied, not committed
  1. Monthly and annual pricing are coupled in three places, and only one of them is a campaign. The annual campaign leg is genuinely independent already. What is not: the global admin discount, the individual admin discount, and — the largest leak — the annual price being built from the monthly campaign price.
  2. The existing schema cannot express "this discount is for monthly". admin_plan_discounts is keyed by plan code alone, and subscriptions.admin_discount_percent is a single column. Both are consumed by one resolver that has no interval parameter, which is why one percentage reaches both cycles.
  3. The fix does not need a second discount system. The campaign table already models exactly the shape required — a monthly leg and an annual leg on the same row. Giving the two admin mechanisms that same pair of columns is additive, keeps every existing bound, and can be back-filled so that no price changes on the day it ships.

01

Where the intervals are joined

Ordered by blast radius. Each row names the exact line, so the finding can be checked without re-deriving it.

C1

A monthly campaign discount changes the annual price

Critical

The annual price is computed from the already discounted monthly price, then given an annual percentage on top. The reverse never happens — the annual percentage never reaches the monthly price — so the leak is one-way and invisible in the data: annual_discount_percent can read 0 while the annual price carries a large discount.

-- 20261011160000_campaign_annual_discount_bounds.sql:124-125
v_original_annual_full := v_original_monthly * 12;
v_final_annual := round (v_final_monthly * 12 * (1 - v_annual_pct / 100.0))::bigint;
                            ^^^^^^^^^^^^^^ carries the MONTHLY campaign discount

Measured worst case on Starter (list 18,000 / month, 216,000 / year): a monthly fixed_amount discount of 13,000 is legal — the UGX 5,000 floor allows it — which sets the monthly price to 5,000. With the annual percentage explicitly at 0, the annual price becomes 60,000 instead of 216,000: a 72% annual discount produced by a monthly-only input. There is no UGX floor on the annual leg, so nothing else catches it.

C2

A global discount cannot say which interval it is for

High

Global rules live one-per-plan with no interval column, so a plan structurally cannot hold two rules. The primary key is what makes plan isolation real; the same key is what makes interval isolation impossible.

-- 20261010120000_admin_subscription_discounts.sql:76-92
create table if not exists public.admin_plan_discounts (
  plan_code text primary key,          -- ← no billing interval
  discount_percent numeric(5,2) not null default 0
    check (discount_percent >= 0 and discount_percent <= 99),
  active boolean not null default true,
  starts_at timestamptz, expires_at timestamptz, reason text, ...
);

Consequently a "global monthly discount" is not expressible. Setting one necessarily moves the annual price by the same percentage — the exact behaviour the brief rules out.

C3

An individual discount cannot say which interval it is for

High

The per-account discount is one numeric column on the subscription, read through a resolver that returns a single number. Every money path passes that number to the pricing function with whichever cycle was requested, so one configured percentage prices a monthly purchase and a yearly purchase alike.

-- 20261010120000:178-191  — one number, no interval in or out
create or replace function public._admin_discount_for_row (s public.subscriptions)
returns numeric ... select case
    when coalesce (s.admin_discount_percent, 0) <= 0 then 0
    when s.admin_discount_starts_at is not null and now () < s.admin_discount_starts_at then 0
    when s.admin_discount_expires_at is not null and now () >= s.admin_discount_expires_at then 0
    else least (greatest (s.admin_discount_percent, 0), 100) end

C4

One resolver collapses both intervals into one number

High

This is the shared root of C2 and C3. The precedence rule — individual wins outright, otherwise the global rule, never stacked — is decided in a function that receives the plan code but not the billing interval, so it has nothing to distinguish intervals by.

-- 20261010120000:198-245  (called from :296 inside the pricing primitive)
create or replace function public._admin_discount_effective (
  p_individual_percent numeric,
  p_plan_code text                       -- ← no billing interval
) returns numeric ...
  if coalesce (p_individual_percent, 0) > 0 then return least (greatest (p_individual_percent, 0), 100); end if;
  select d.discount_percent into v_global from public.admin_plan_discounts d
   where d.plan_code = v_plan and public.admin_plan_discount_is_active (d);

The consuming line is the single place where money is discounted, and it applies one value to whichever cycle was selected two lines above:

Medium

C6

The admin screen offers no way to choose an interval

Medium

src/components/internal-admin/v2/pages/AdminSubscriptionDiscountsPage.tsx is the only page that writes subscription discounts, and it has no monthly/annual control anywhere. One percentage input feeds both the global and the individual form, and the preview beneath each shows a monthly line and an annual line derived from it. The saved-individual table does not render an annual price at all.

The one pricing screen that does have an interval field is AdminPricingCampaignsPage.tsx:919-1003, whose grid carries a separate Annual % column capped at 90. That contrast is useful: the campaign mechanism already solved this problem, and it is the shape the admin mechanisms should copy.

C7

Negotiated offers are interval-blind in two directions

Medium

org_billing_offers stores a flat amount with no interval column. Two consequences, both real but neither a percentage coupling:

  • Settlement. The mark-paid amount guard accepts any amount matching a live offer for that organization, so an offer negotiated for one period length can settle a period of the other interval. The period granted still follows the subscription's own interval, so the exposure is a mis-scoped period, not a mispriced amount.
  • Fulfilment. 039:257, 291-298 hard-codes + interval '365 days' and leaves billing_interval untouched, so a monthly shop whose offer is fulfilled silently receives a year. A monthly negotiated deal cannot be expressed through this mechanism at all.

Fulfilment also resolves the subscription with the older order by created_at desc limit 1 rule rather than the shared _subscription_latest_for_org resolver that every other path was moved onto.

C8

Display artefacts that will read oddly once the intervals diverge

Cosmetic
  • The annual pricing card prints Save {annualDiscountPercent}% taken from the campaign layer while the struck-through and final figures beside it carry the global admin discount — so a 50% global rule currently shows a 50%-reduced price next to "Save 20%".
  • The checkout shows a savings line for monthly quotes only; an annual quote deliberately shows none (src/lib/paymentCheckout.ts:230-238). Correct today, and it will need a decision once annual discounts become real and independent.
  • Hard-coded annual fallbacks in src/lib/i18n.ts:7756-7761, 15214-15219 quote UGX 172,800 / 345,600 / 787,200 and "Save 20%" when the price book fails to load.
  • The shop console's placeholder amount falls back to the book's monthly figure regardless of the subscription's interval (EnterpriseShopConsolePage.tsx:207); the authoritative server amount replaces it.

03

Proposed data model

The campaign table is the precedent: one row carries a monthly leg and an annual leg. Reusing that shape means no new concept, no new table, and no second discount system.

Global rules — mirror the campaign row

alter table public.admin_plan_discounts
  add column if not exists annual_discount_percent numeric(5,2) not null default 0
    check (annual_discount_percent >= 0 and annual_discount_percent <= 99);

-- Backfill: today's single percent governs both cycles, so copy it into the
-- annual leg. Every price is therefore identical on the day this ships.
update public.admin_plan_discounts
   set annual_discount_percent = discount_percent
 where discount_percent <> annual_discount_percent;

Individual rules — same pair, on the subscription

alter table public.subscriptions
  add column if not exists admin_discount_percent_annual numeric(6,2) not null default 0
    check (admin_discount_percent_annual >= 0 and admin_discount_percent_annual <= 100);

update public.subscriptions
   set admin_discount_percent_annual = admin_discount_percent
 where coalesce (admin_discount_percent, 0) > 0;

Resolution becomes interval-aware

_admin_discount_for_row (s subscriptions, p_interval text)          -- returns the individual leg for that cycle
_admin_discount_effective (p_individual_percent, p_plan_code, p_interval text)

-- Inside subscription_payment_plan_amount the cycle is already resolved at :286,
-- so the call site simply passes it through:
v_discount := public._admin_discount_effective (p_admin_discount_percent, v_plan, v_cycle);

Both helpers are internal: they carry no EXECUTE grant for public, anon or authenticated, so widening their signature is contained. subscription_payment_plan_amount keeps its exact signature and therefore its ACLs — quote, create, expected-amount, mark-paid and free activation need no re-grant.

The campaign fix is one line, in two places

-- server: a new migration overriding _pricing_compute_plan_row
- v_final_annual := round (v_final_monthly      * 12 * (1 - v_annual_pct / 100.0))::bigint;
+ v_final_annual := round (v_original_monthly    * 12 * (1 - v_annual_pct / 100.0))::bigint;

// client mirror: src/lib/subscriptionPricing.ts:91
- const finalAnnual = Math.round(finalMonthly    * 12 * (1 - annualPct / 100));
+ const finalAnnual = Math.round(originalMonthly * 12 * (1 - annualPct / 100));
This is a no-op whenever no monthly campaign discount is running. Business list is 36,000 / month with a 20% annual default, so the annual price is 345,600 either way — 30,000 × 12 × 0.8 and 36,000 × 12 × 0.8 only differ because the first carries a 6,000 monthly discount. The change is visible only during a monthly campaign, and there it raises the annual price to the list-based figure. That consequence is unavoidable if monthly campaigns are to leave annual pricing alone; it is decision D2 below.

The independence suite to add

The point of these is the negative: change one interval, prove the other price did not move. Every case runs against the real migration chain in the pglite harness.

  • Global. Save a monthly global rule; assert the annual price is byte-identical before and after. Repeat in the other direction. Assert an annual-only rule leaves the monthly price untouched.
  • Individual. Set a monthly percentage on a subscription; assert its annual quote does not move. Set an annual percentage; assert the monthly quote does not move.
  • Campaign. With a monthly campaign discount live, assert the annual price equals the same campaign's annual leg applied to the list monthly price — i.e. the monthly discount contributes nothing. The reverse — an annual campaign change moving the monthly price — should already fail to reproduce.
  • No stacking. An individual monthly rule and a global monthly rule together must price as the individual one alone, exactly as today. Same for annual. And the cross case: an individual monthly rule must not suppress the global annual rule.
  • Bounds preserved. Global and individual 0–99 including the two new columns; campaign monthly 90% clamp and the UGX 5,000 floor; campaign annual 0–90 through the CHECK, the RPC and the clamp.
  • Money paths agree. For a subscription on each interval, quote, create, expected-amount and mark-paid must all return the same figure the pricing primitive returns — the existing parity assertions, re-run against the interval-aware resolver.
  • Free activation. 100% on the monthly leg must not permit a free annual period, and vice versa — the eligibility check reads the subscription's own interval.
  • Client/server parity. The existing pricingCampaignsAdmin.sql.integration.test.ts:260 matrix already crosses every monthly branch with an annual percent and compares client to server; it should keep passing unchanged, and is the guard that the mirror was edited in lockstep.
06

Decisions needed before implementation

D1

What happens to discounts that already exist?

Existing global and individual rules were configured when one percent meant both intervals. The back-fill decides whether separating the intervals changes any live price.

ACopy the existing percent into both legs. Every price is identical on the day it ships, and independence begins from that point. Nothing to explain to a customer.
BTreat the existing percent as monthly only. Cleaner semantics going forward, but every organization currently buying annually sees its price rise to the campaign or list figure the moment this deploys.

Decided: A. Both legs are back-filled from the percent each row already carried, so the migration is price-neutral on the day it ships.

D2

The annual price rises during a monthly campaign — confirm that is wanted

Separating the intervals means the annual price stops inheriting the monthly campaign discount. During a monthly promotion the annual card therefore shows the list-based annual figure, which is higher than what it shows today. There is no way to satisfy "monthly campaigns must never affect annual pricing" and keep the current annual figure at the same time.

AAccept it, and compensate with the annual leg. During a monthly promotion, set the campaign's annual percentage explicitly if the annual price should also fall. The campaign form already has that field.
BLeave the campaign base as it is and isolate only the two admin mechanisms. This contradicts the brief's "monthly campaigns must never affect annual pricing", so it is listed only for completeness.

Decided: A. The annual leg is a percentage of the annual list price, and the campaign form's Annual % field is how a promotion reaches the year. The pricing-card copy that this consequence needs is now in place — see below.

D3

Two columns on one row, or a row per interval?

Two columns mirror pricing_campaign_plan_discounts exactly and keep one shared window, one active flag and one reason per rule. A row per interval (primary key (plan_code, billing_interval)) would additionally allow separate windows per interval, at the cost of a composite key, a duplicated window per rule, and two rows per plan on the admin screen.

Decided: two columns, shared window. One window, one active flag, one reason per rule; two rates inside it. Separate per-interval windows would be a different and larger change.

D4

Does an individual monthly discount still suppress the global annual one?

Today, any individual discount beats the global rule for both cycles. Once the legs are separate, the resolver has to decide what a zero on one leg means. Either it falls back per interval — monthly zero falls back to the global monthly rule, annual zero to the global annual rule — or an individual rule on either leg continues to suppress both global legs.

Decided: fall back per interval. An individual monthly leg beats the global monthly leg; the annual leg is resolved on its own, so an account with an individual monthly discount still receives the global annual one. Zero keeps meaning "no rule of my own" on each leg.

D5

Are the 11 October discount migrations live in production?

Migrations 20261011120000 through 20261011170000 — the billing-role gate, the mark-paid amount guard, the annual bounds, the public price book — are committed and green locally. Whether they have been applied to the production project cannot be determined from this working copy, and the new migration overrides functions several of them define.

Still open, and it gates the deploy rather than the code. The new migration is written on top of them either way. But if they are not yet applied, the deploy must carry the whole set in order — and the web bundle must ship in the same step, because the admin screen's RPC signatures change here: admin_plan_discount_save, admin_subscription_discount_save and admin_discount_preview each gain an annual parameter, and the old signatures are dropped so no overload can linger.

07

Adjacent issues found, not part of this change

Recorded so they are not lost, and deliberately excluded from the proposed fix.

  • Offer fulfilment always grants a year (039:257, 291-298) and still uses the superseded subscription-resolution rule. A monthly negotiated deal cannot be expressed at all.
  • No UGX floor on the annual leg. The 5,000 floor is monthly-only; the annual figure is bounded solely by the 90% cap. Probably intended, but the floor guarantee does not hold for annual prices.
  • final_monthly_with_discount_ugx in the overview is now the same expression as final_monthly_ugx (20261011150000:394-395), so the name no longer describes the value.
  • The save RPC quotes the configured percent, not the effective one (20261011150000:311-312), so a future caller reading those prices would see a figure the shop may not be charged.
  • admin_discount_preview re-derives the discount arithmetically rather than calling the pricing function, so its agreement with checkout is coincidence rather than construction. Worth folding into the new migration while the function is open.
No migration has been run, no function deployed, no production data touched, nothing committed. Every price quoted here is either read from the source or measured in the pglite harness at src/test/sqlIntegration, which replays the real migration chain in production order. Two things remain outside this change: the deploy-order question in D5, and the adjacent findings in section 07.
