Subscription Discounts Audit

Full trace of the pricing-campaign, global and per-account discount systems — what each one does today, where the money path actually is, why a saved global discount looks inert, and the decisions required before any fix.

repo HEAD ad66f47f prod deploy ad66f47f remote ledger: both migrations applied 21 scenarios run on an isolated database 71 pinned tests green no production writes

Bottom line

Three answers, up front

1

The system is live and it does discount. Both discount migrations are in the production migration ledger, the deployed frontend is this commit, and an isolated run of the real SQL chain shows a global rule, an account rule and a campaign all reaching the amount that checkout charges — including the 99% case at UGX 360 and a 100% case at UGX 0.

2

The global discount only ever appears inside a checkout quote. It never edits an existing subscription, and every other screen — the public pricing page, the in-app upgrade page, and the admin console's own “Mark paid” amount — reads a price book that does not contain it. The one path where it genuinely never applies is the manual/offline payment. That is the whole of the “it doesn't activate” experience.

3

The UGX 5,000 floor belongs to campaigns, not to discounts. It is enforced server-side in one function (_pricing_min_final_monthly_ugx) that only campaign pricing passes through, mirrored in the admin form. The admin discount is applied after it and is deliberately not floored. Removing the floor would change campaign pricing only; it would not unlock anything the Subscription Discounts screen cannot already do.

3 · Precedence

Three mechanisms, one arithmetic order

Everything is decided in one place: subscription_payment_plan_amount calls _admin_discount_effective once, which is the only code that ranks the rules. Quote, create and expected-amount all route through it, so they cannot disagree with each other.

Precedence as implemented today. “Stacks” means the two percentages add or apply one after the other.
OrderLayerSource of truthHow it combinesBound
1Campaign discountpricing_campaigns + pricing_campaign_plan_discountsApplies to the canonical price. Nothing stacks underneath it.90% clamp, UGX 5,000 monthly floor
2Account discountsubscriptions.admin_discount_percent (+ window columns)Replaces the global rule outright — never added to it, and it wins even when it is the smaller number.0–99 written; 100 readable
3Global plan discountadmin_plan_discountsUsed only where the account has no in-window discount of its own. A lapsed account discount falls back here, not to list.0–99
4No discount—Effective percent 0.—

A zero is not a rule

admin_discount_percent = 0 means “no account rule”, so the global rule takes over. There is currently no way for an account to opt out of a global discount.

Windows are server-enforced

Expiry is resolved from the subscription row on every money path, so a lapsed discount cannot be applied by quote, create or the expected amount — and it cannot be talked back into force by a client.

The campaign is always underneath

A 50% campaign with a 99% discount prices at 1% of the campaign price (18,000 → 180), not 1% of list. The floor is applied before the discount, so a discount can go far below UGX 5,000.

5 · The complaint

Why the global discount looks like it never activates

In order of how much each one explains. The first two are the answer; the rest are the smaller traps that produce the same impression.

1. There is nothing to activate — the price is computed per payment, never stored

A subscription row holds a plan, a billing interval and a period, not a price. Saving a global rule writes one row to admin_plan_discounts and touches no subscription at all — proven in scenario 11, where the subscription's plan, status, period end and discount column were byte-identical before and after, and pinned by an existing test (“does not rewrite an existing subscription's plan or period when a discount changes”). So a shop that is already paid up sees no change whatsoever until its next renewal, and there is no job, trigger or email that “applies” anything. If you were expecting a shop's plan to visibly flip to a discounted price, that event does not exist in this design.

2. Every screen except the checkout reads a price book that has no admin discount in it

public_subscription_pricing() — the anon-readable function behind the public pricing page, the in-app upgrade page and the shop console's “Mark paid” amount — reads the canonical book and the campaign layer only. Measured: with a live 50% global rule, that function returned 36,000 while the checkout quoted 18,000. So the discount is real at the moment money is taken and invisible everywhere else. The sharpest consequence is the third surface: the admin console's “Mark paid · UGX 36,000” button suggests the full list price for a discounted shop, and admin_subscription_mark_payment writes whatever amount it is handed without ever comparing it to the price the discount implies.

3. A payment already in flight keeps its amount

Once an intent exists, the amount is frozen in the payment row. The settlement callback validates the checkout snapshot against its own ledger amount and never re-prices, and the checkout UI deliberately stops re-quoting from that point. Granting a discount after the shop pressed Pay does not change what that payment will cost.

4. The admin screen shows a price for rules that are not live

The global table's “Effective price” column is a formula on the stored percentage: it ignores active and both window columns. An inactive 50% rule still renders “36,000 → 18,000” beside a Status chip reading “Inactive”. The per-account table does this correctly, which makes the two halves of the same page disagree about what “effective” means.

5. An account rule hides the global one — including while it is merely configured

The account rule replaces the global one outright and wins even when it is the smaller number (40% global vs 5% account quoted at 34,200). If a shop was given an account discount at any point, a later global change is invisible for that shop by design — and while a future-dated account rule is pending, the shop is on the global rule, not on list.

6. Global rules are keyed by plan code, not by plan

A rule is stored per plan code and only the three catalog codes can be given one. A subscription sitting on any other plan code — a legacy or bespoke code — will never match the rule, however it is named.

8 · Integrity

Security and financial controls

ControlVerdictDetail
Server-side amount validationpassesQuote, create and expected-amount all compute the amount from the plan, the campaign and the resolved discount. The client only ever states what it believes the price is.
Mismatch rejectionpassessubscription_payment_create returns amount_mismatch with the expected figure when a supplied amount differs, and writes nothing. Note the parameter is optional: an omitted amount simply means the server writes its own.
Zero-value protectionclient onlyThe client refuses to create a fully-discounted checkout; the server will happily write a pending 0-amount payment (D5). No free entitlement is granted for it — the manual path skips the period advance at 0 — but a junk intent is created and must time out.
Authorization of admin RPCstoo broadEvery pricing RPC authorizes “any active internal admin” while the UI restricts the screens to four billing roles (D2). No discount can be granted by a shop user: owners, cashiers and unrelated users are refused, verified in the pinned suite.
RLS and tenant isolationpassesadmin_plan_discounts has RLS on with no policies and all privileges revoked — no client role can read or write it directly, verified against production and in the suite. Subscription rows are SELECT-only for clients since the client-DML lockdown. One organization's discount does not reach another organization.
Client cannot set a pricepassesNo discount percentage is ever accepted from a shop client. The account discount is read from the subscription row server-side; the amount written to the ledger is the server's own.
History and existing terms preservedpassesChanging a discount rewrites no subscription, no period and no settled payment. The ledger amount is immutable once written (state-guard trigger), and settlement never re-prices.
No duplicate or stacked discountspassesOne row per plan by primary key, so a re-save edits rather than accumulates; the account and global rules are selected by a single ternary, so they can never both apply.

9 · Decisions

What I need from you before building anything

A · Should a manual “Mark paid” honour the discount?

1 · Server computes the amount2 · Keep it manual, show the discounted figure3 · Leave as is

Recommend 1 with 2's display: the console should show the discounted price and the RPC should reject an amount that differs from it. This is the only defect where money is wrong today, and it is the most likely thing you actually saw.

B · Is an “individual” discount for a shop or for an account?

Account-wide (today)Per shop

Recommend keeping account-wide — the schema allows one live subscription per organization, so per-shop pricing would need a new column and a precedence rule of its own. Relabel the screen to say “account”, and show how many shops it covers.

C · Should a global plan discount ever reach zero?

Cap at 99% everywhereAllow 100% and settle it without a provider

Recommend 99% for anything that creates a payment, plus an explicit “grant a free period” action if you want it. Today a 100% account discount can be written by SQL only; the setters refuse it.

D · Should the public price page reflect a global plan discount?

Yes — show it wherever the plan is shownNo — checkout only

This is the real fork. A “global” discount that nobody can see outside checkout is what makes the feature feel broken; folding it into the public book makes it behave like a campaign. Note the reverse risk: a purely internal goodwill rate would then be advertised.

E · Which roles may grant subscription discounts?

The four billing roles the UI showsAny internal admin (today)

Recommend the four, matching canManageBillingOffers. The server is currently broader than the screen, which is the wrong direction for a control that can give away 99% of revenue.

F · Renewal and expiry semantics

As today: rule in force at payment time winsDifferent

Recommend keeping it and documenting it: a discount expiring mid-period is not prorated or credited, and a payment already in flight keeps its amount. If you want “honour the discount for one more renewal”, that is a new rule, not a fix.

10 · Plan

Minimal ordered implementation, after your approval

  1. Decide A–F. Every step below depends on at least one of them; none of this should be built before the answers exist.
  2. Migration: the manual payment path (D1, decision A). Add an internal-gated RPC returning the amount the discount implies for a subscription, and have admin_subscription_mark_payment refuse a mismatched amount the way subscription_payment_create already does. Then point the shop console's suggested amount at that RPC instead of the public book. Tests: extend the admin-discount SQL suite with mark-paid cases, including a discounted shop and a 0 amount.
  3. Migration: authorization (D2, decision E). Tighten the gate on the two discount setters to the billing roles, leaving campaign RPCs untouched unless you want them aligned too. This is a behaviour change for support_admin and field_agent — confirm before applying, since it can break a workflow you rely on. Test: each role's expected outcome, mirroring adminRoles.ts.
  4. Migration: campaign annual bound (D3). Clamp the annual percentage in the campaign pricing function and add a CHECK on the column, with the same “discount_below_minimum”-style refusal at save time. This one changes a contract the campaign tests pin, so the existing tests are updated deliberately, not silently.
  5. Migration: pricing-helper hygiene (D9). Revoke PUBLIC EXECUTE on the internal _pricing_* helpers and add the internal-staff check to the audit helper. No caller outside the definer functions needs them.
  6. Frontend: the Subscription Discounts screen (D4, D6, D7, D10). Show the account-discount preview through p_individual = true; make the global “effective price” respect active and the window; state plainly that the discount covers the whole account and how many shops that is; unify the plan label and add the missing cross-links.
  7. Frontend: the numbers people read (D8, D11, decision D). Recompute the displayed saving after the floor; render or drop the annual figure; if decision D is “yes”, feed the global rule into the public book so the pricing and upgrade pages agree with checkout.
  8. Zero-value policy (D5, decision C). Whichever way C goes, put the guard on the server, not only in the client: either refuse to create a zero-amount intent or settle it without a provider. Keep the existing client guard — it is defence in depth, not the fix.
  9. Verification before deploy. Both pinned SQL suites plus the new cases, on a disposable Postgres rather than the shared one; a browser pass over both admin screens and a shop checkout with a live rule; confirm no unrelated dirty files are staged with it.
  10. Deploy. Frontend: pushing to main auto-deploys; verify by grepping the served chunk, not by waiting. Database: the migrations must be applied by you — the Supabase CLI cannot run in this environment and db push is on the deny list. Apply the migrations before the frontend that depends on them.
Rollback. Every server change above is create or replace on an existing function or an additive CHECK, so reverting means re-applying the previous body — each migration in this repo already carries its predecessor's definition in its header for exactly that. No table is dropped, no row is migrated, and no historical payment is rewritten. The two pinned SQL suites are the revert gate: if they go red, the change is wrong, not the test.
